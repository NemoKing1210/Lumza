# AGENTS.md

Lumza: a Windows tray app that controls external monitors (brightness, contrast, volume) over DDC/CI. Rust core, Tauri 2 shell, Svelte 5 UI in WebView2. Windows only; there is no Linux/macOS build.

See [CONTRIBUTING.md](CONTRIBUTING.md) for the full contributor guide and [README.md](README.md) for the product.

## Layout

| Path | What lives there |
| --- | --- |
| `crates/lumza-core` | Hardware-independent logic: DDC/CI backend (`dxva2.rs`), capabilities parser (`caps.rs`), scaling and calibration (`scale.rs`), settings store (`store.rs`), schedule maths (`schedule.rs`), mock backend (`mock.rs`). Unit-tested. |
| `crates/lumza-cli` | `lumzactl`, a diagnostic CLI (`list`, `get`, `set`, `caps`). |
| `src-tauri` | The app: `controller.rs` (single owner of monitor state), tray, flyout/OSD windows, hotkeys, scheduler, updater, `i18n.rs`. |
| `ui` | Svelte 5 front end: flyout (`App.svelte`), settings window (`Settings.svelte`, `ScheduleSettings.svelte`), OSD (`Osd.svelte`). IPC wrappers in `ui/src/ipc.ts`. |
| `locales` | One `<code>.json` per language, shared by the UI and the Rust side. `en.json` is the reference and the fallback. |

## Commands

```bash
npm ci && npm --prefix ui ci                  # install
LUMZA_MOCK=1 npm run tauri dev                # run with mock monitors (no hardware)
cargo run -p lumza-cli -- list                # talk to real monitors

cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cd ui && npm run lint && npm run typecheck && npm test
```

The frontend is embedded into the app at compile time: run `npm --prefix ui run build` before `cargo build`/`cargo clippy` on `src-tauri` if `ui/dist` is stale or missing. CI runs exactly the checks above; run them before finishing a change.

## Architecture rules

- Tray, hotkeys, schedule, OS events and the UI never touch monitors directly. They send commands to the **controller**, which coalesces writes (only the latest value per feature is queued) and hands them to the monitor's own worker thread.
- Be gentle with the hardware: no polling timers, no write loops. DDC/CI writes wear a monitor's EEPROM.
- Settings live in `settings.json` and are changed through `update_settings(patch)`, a JSON merge patch (objects merge, `null` deletes, arrays replace whole). Every new field needs a serde default and, if it has limits, a clamp in `Settings::sanitize`. Bump `SCHEMA_VERSION` and add a `migrate` step only for changes defaults cannot cover. Mirror new fields in `Settings` in `ui/src/ipc.ts`.
- Adding a Tauri command: define it in `src-tauri/src/main.rs`, register it in `generate_handler!`, and add a typed wrapper in `ui/src/ipc.ts`.

## Localisation

- Every user-visible string goes into **every** `locales/*.json` (en, ru, es, de, fr, pt, zh) with the same keys and `{placeholders}`. Tests in both `ui/src/i18n.test.ts` and `src-tauri/src/i18n.rs` fail when files disagree or the UI references a missing key.
- UI strings use `t("key")`; backend strings use `i18n::t(lang, "be.…")` (backend keys are prefixed `be.`).
- `general.language` is a language code or `"auto"` (default): follow the Windows language, English when unsupported. The backend resolves it in `i18n::t`; the UI gets the resolved system language through `get_system_language`.
